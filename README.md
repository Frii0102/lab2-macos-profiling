# Лабораторна №2: проста програма на Mac ARM64

Статус: програма, заміри часу, два FlameGraph та розбір асемблера готові.
Енергія ще не виміряна. Інструкції, цикли та IPC вже отримано;
cache misses недоступні. Це не завершений звіт за всіма пунктами.

## Що робить програма

Масив — список чисел. Для кожного числа обчислюємо `число * 2 + 1`.
Наприклад: `[0, 1, 2]` → `[1, 3, 5]`. Повторюємо ту саму обробку,
щоб вона тривала достатньо довго для вимірювання. Перевіряємо кожен результат.

- `main.cpp`: створює дані, викликає обробку, перевіряє результат.
- `kernel.cpp`: сам цикл обробки, лише кілька рядків.
- Файли компілюються окремо, без LTO. Тому оптимізатор не може викинути
  всі повторні виклики як непотрібні. Однакова структура для O0 та O3.
- `-O0`: без оптимізацій; `-O3`: оптимізації компілятора.
- Пам’ять виділяється й перевірка виконується поза внутрішнім таймером.
  `/usr/bin/time` вимірює весь процес, включно з цими етапами.

## Запуск

Відкрити термінал у цій теці. Нічого вводити всередині програми не потрібно.

```bash
bash build.sh
./build/program_O0 10 1
./build/program_O3 10 1
bash measure.sh
```

Для 10 елементів checksum має бути 100, для 1 000 000 — 1 000 000 000.
Обидві версії мають вивести `check=OK` та однакову checksum.
Числа у команді — кількість елементів і кількість повторень.
Порівнюємо лише однаковий обсяг роботи. Закрийте зайві програми,
залиште однаковий режим живлення; між серіями дайте ноутбуку охолонути.

## Час та статистика

`measure.sh` запускає `/usr/bin/time -l` п’ять разів на кожну версію
у змінному порядку. Сирі логи залишаються у `results/`.

- `real`: час від запуску до завершення.
- `user`: процесорний час у коді користувача.
- `sys`: процесорний час роботи ядра для процесу.
- `maximum resident set size`: максимальна резидентна пам’ять; у macOS байти.
- `page reclaims`: minor faults, не обов’язково читання диска.
- `page faults`: major faults; відсутність не доводить відсутність усього I/O.
- context switches: перемикання виконання між потоками/процесами.

На цьому Mac `time -l` також надає `instructions retired` і `cycles elapsed`.
Скрипт summarize.py обчислює IPC = instructions/cycles для кожного запуску.
Це частковий аналог статистики perf, не всіх подій `perf stat -d`:
cache misses і branch misses не отримано. Установлено лише Command Line Tools,
тому `xctrace` наразі відсутній. Для нашого профілю використано sample.
Джерело реалізації time: https://github.com/apple-oss-distributions/shell_cmds/blob/main/time/time.c

## Профіль та FlameGraph

Початковий шлях без Xcode: вбудований `sample` і відкритий FlameGraph.
Це вибірки стеків процесу, не точний еквівалент Linux on-CPU `perf`.
`sample` може показувати очікування; сторонній конвертер приховує частину
відомих блокувальних стеків. Наш процес однопотоковий та обчислювальний.

```bash
bash profile.sh 0
bash profile.sh 3
git clone https://github.com/brendangregg/FlameGraph.git tools/FlameGraph
# Підставити фактичні шляхи, які вивели попередні команди:
bash flamegraph.sh results/profile-O0-ДАТА/sample.txt O0
bash flamegraph.sh results/profile-O3-ДАТА/sample.txt O3
```

Результат — SVG, який відкривається у браузері. На захисті показати
запис → sample.txt → folded → SVG. Саме sample.txt також містить дерево
та зведення функцій для аналізу, але не є файлом perf report.

Ширина прямокутника — частка вибірок стеків, які містять функцію.
Висота — глибина викликів. Зліва направо НЕ час. Колір звичайного графіка
не означає температуру, швидкість чи енергію. Оптимізована версія може
мати майже такий самий графік: вона просто робить більше роботи за секунду.
Профілюємо по 10 секунд усередині 12-секундного запуску: кількість повторень
різна, тому ці запуски НЕ використовуємо для висновку про енергію однакової задачі.

Інструмент і ліцензії: https://github.com/brendangregg/FlameGraph
Опис: https://www.brendangregg.com/FlameGraphs/cpuflamegraphs.html
Використовується їхній `stackcollapse-sample.awk` та `flamegraph.pl` без
приписування авторства собі. Commit інструмента записується поряд із SVG.

## Асемблер та SIMD

Дивимося `assembly/kernel_O0.s` і `assembly/kernel_O3.s`.
SIMD — одна інструкція працює з кількома числами. На ARM64 шукаємо
операції над векторними регістрами на кшталт `v0.4s` (чотири 32-бітні числа).
Наявність SIMD треба підтвердити фактичним асемблером, а не самим ключем O3.
AVX — не інструкції цього ARM-процесора; тут аналізуємо NEON.

## Енергія: ще не виміряна

Скрипт підготовлений: `bash run-energy.command`. Потрібне локальне введення
пароля Mac. Він збирає 3 серії O0/O3 з однаковими 60 000 повтореннями,
фон до і після кожного запуску, зберігає сирий лог та energy-summary.md.
Тести парсера синтетичні й НЕ є результатами енерговимірювання.

Цей пункт НЕ закрито автоматично замірами часу. `powermetrics` потребує
адміністративних прав. Пароль вводиться тільки локально в терміналі, не в чаті.
Він надає оцінки потужності доступних підсистем, а не гарантовано всього Mac.
`--show-process-energy` показує Energy Impact, не джоулі окремого процесу.

План: записати фон, потім окремі запуски O0 та O3 з однаковою кількістю
елементів і повторень, синхронізувати часові межі з логом потужності.
Енергія за інтервалами: `E = sum(P_i * dt_i)`; вати × секунди = джоулі.
Оцінка додаткової енергії: `E_incremental = E_load - P_idle * T`.
Це оцінка приросту споживання виміряних підсистем, НЕ точна енергія процесу.
Негативне значення не обрізаємо до нуля: це ознака шуму/проблеми експерименту.
Для вимірювання всього ноутбука бажаний зовнішній вимірювач; без нього
треба погодити з викладачем межі вимірювання та спосіб оцінювання.
